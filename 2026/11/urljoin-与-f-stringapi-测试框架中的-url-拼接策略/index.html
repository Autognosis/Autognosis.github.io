urljoin 与 f-string：API 测试框架中的 URL 拼接策略

在 API 测试框架中，URL 拼接是一个基础但容易被低估的细节。常见做法有两种：使用 urljoin 进行 URL 语义合并，或使用 f-string 进行显式字符串拼接。两者行为差异明显，适用场景也不同。

核心结论是：urljoin 做的是“URL 语义合并”，f-string 做的是“字符串拼接”。前者会按 RFC 3986 的规则进行规范化处理，后者不参与 URL 语义解释，所见即所得。在 API 测试框架中，通常更需要后者。

本文梳理 urljoin 在 API 测试场景中容易引发问题的四类行为，并说明为什么显式字符串拼接更适合同步可控的 API 请求构造。

urljoin 的四类典型问题

urljoin 的设计目标是处理相对链接，因此会依据 URL 语义执行较多规范化。问题在于，这些“智能”行为在测试场景中经常与预期不符。

问题 1：绝对路径会覆盖 base_url 的路径

urljoin 认为以 / 开头的 endpoint 是“绝对路径”，会丢弃 base_url 的路径部分：

1urljoin("https://api.example.com/v1/", "/users")
2# 'https://api.example.com/users'   ← /v1/ 被丢弃

若 base_url 为 https://xxx.com/api/v1/，endpoint 传入 /posts，拼接结果为 https://xxx.com/posts，版本号路径直接消失。f-string 不会产生该行为：

1f"{'https://api.example.com/v1/'.rstrip('/')}/{'/users'.lstrip('/')}"
2# 'https://api.example.com/v1/users'

问题 2：路径穿越 .. 和 . 会被静默规范化

1urljoin("https://api.example.com/v1/", "users/../admin")
2# 'https://api.example.com/v1/admin'   ← .. 被处理掉了

在安全测试等场景中，若需要验证服务器对 ../ 的处理，urljoin 会提前将测试数据规范化，导致实际请求路径与构造路径不一致。f-string 则原样保留路径片段。

问题 3：// 可能导致域名被替换

1urljoin("https://api.example.com/", "//evil.com/path")
2# 'https://evil.com/path'   ← 协议相对 URL，域名被替换

此时并非路径拼接，而是主机部分被替换。f-string 拼接结果为 https://api.example.com///evil.com/path，请求仍位于原域名下。

问题 4：; 被 urlparse 解析后丢失

1urljoin("https://jsonplaceholder.typicode.com/", "posts/;")
2# 'https://jsonplaceholder.typicode.com/posts/'   ← ; 丢失

根因是 urljoin 内部依赖 urlparse，; 被解析到 params 字段后，重组时未保留。f-string 不会改变原始字符。

行为对比

行为urljoin(base, endpoint)f-string + rstrip/lstrip
拼接逻辑URL 语义合并（RFC 3986）纯字符串拼接
endpoint 以 / 开头覆盖 base 的路径仅去除一个 /，路径保留
.. / .静默规范化原样保留
// 开头可能替换域名原样保留在路径中
;、?、# 等保留字符可能被解析重组丢失原样保留
可预测性较低，依赖 RFC 规则较高，所见即所得
适合场景爬虫解析页面中的相对链接已知 base_url 与已知 endpoint 的 API 调用

适用场景划分

适合使用 urljoin 的场景：endpoint 形态不可预知，可能为相对路径、绝对路径、协议相对 URL 或包含 ../ 的路径。典型场景是爬虫从 HTML 中提取链接后转换为绝对 URL。此时 urljoin 的语义合并能力符合需求。

适合使用 f-string 的场景：base_url 来自固定配置，endpoint 由代码显式构造，例如 /posts/{id}、/users/{uid}/orders，两端均完全可控。此时不需要 URL 语义合并，只需要可靠地连接两段字符串，并确保任何字符都不被静默修改。

API 测试框架通常属于后者。

推荐实现

在 API 测试框架中，请求方法可采用如下拼接方式：

1def request(self, method, endpoint, **kwargs):
2    url = f"{self.base_url.rstrip('/')}/{endpoint.lstrip('/')}"
3    ...

该写法包含以下约束：

  • rstrip('/') 保证 base_url 末尾不保留 /；
  • lstrip('/') 保证 endpoint 开头不保留 /；
  • 中间固定插入一个 /，避免产生 //；
  • 不执行 URL 解析、规范化或字符处理，;、.. 等字符原样传递给 requests。

总结

urljoin 适用于“链接形态不可预知”的场景；f-string 适用于“拼接目标完全明确”的场景。API 测试框架属于后者。显式字符串拼接更透明、更可预测，也能避免测试数据在构造阶段被意外修改。
